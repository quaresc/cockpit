The repo

plugin/The Claude Code half: hooks, commands, the side-browser skill and their tests. It fetches from your sessions' connectors, one session at a time, and hands the result to the hub.
herdr/The herdr half. herdr/tui is one cockpit binary in Rust: the space apps and the hub.
app/The Herdr app half: a layout (layouts/cockpit.json), one mod (mods/cockpit/) drawn natively by Herdr from JavaScript, and its keys.
docs/screenshotsThe tooling that regenerates every screenshot on made-up data.
site/This site: plain HTML and one stylesheet, deployed by .github/workflows/pages.yml with the screenshots from docs/ and the changelog copied in.

The hub

The hub is the only writer. It keeps the data and a week of history in ~/.cache/cockpit/store.redb (mirrored as JSON), pushes each change to the apps, and queues their button presses for the next session to carry out. It listens on a unix socket for the herdr apps and on 127.0.0.1 with a token for the Herdr app.

Herdr window ── mods/cockpit (JS) ── TCP 127.0.0.1 (hub.json: port, token) ──┐
herdr TUI ───── cockpit apps (Rust) ── unix socket ────────────────────────────┤── cockpit hub ── store, views, actions
Claude Code ─── plugin hooks ─────────── cockpit CLI / socket ─────────────────┘

The Herdr app half

One mod, many views

Herdr refuses imports outside a mod's folder, so every place uses the cockpit mod with props.app; main.js maps names to view classes.

Rust keeps the logic, JS draws

A view's model is built by its app crate and served by the hub; edits are hub actions. The terminal and the GUI never drift.

Two frontends

cockpit_core::frontend picks herdr or the Herdr app per request, so anything that opens, focuses or types into a window goes to the right one.

Adding an app's view takes three steps: a gui.rs in the app crate with view, act and dirs, registered in herdr/tui/cli/src/gui.rs; a JS class in mods/cockpit/<app>.js added to VIEWS in main.js; and every terminal key and action as a visible button with its key hint. cockpit_todo::gui and todo.js are the references. Build every screen from the design kit in ui.js (shadcn/ui's components on Herdr's theme). app/README.md has the details.

Testing

The Herdr app sandbox is a separate Herdr window on a fake HOME with the acme demo world and its own hub, with the mod copied again on every save in app/:

COCKPIT_SANDBOX=$TMPDIR/cockpit-gui-inbox sh app/sandbox.sh start
sh app/sandbox.sh show todo; sh app/sandbox.sh key j; sh app/sandbox.sh shot /tmp/x.png; sh app/sandbox.sh check
sh app/sandbox.sh light; sh app/sandbox.sh stop

herdr-app check must pass and a screenshot must look right in both themes before a view is done; cargo test for the crates touched. CI (.github/workflows/check.yml) runs shellcheck, parses the app's layout, keys and modules, validates and tests the plugin, and runs clippy and the Rust tests.

Screenshots

The screenshots are the real apps on made-up data. docs/screenshots regenerates the terminal ones; sh docs/screenshots/app_shots.sh [view ...] shoots each Herdr app view in the sandbox window, dark and light, into docs/app/.

Releases

Both halves share one version with the apps: plugin/.claude-plugin/plugin.json, herdr/herdr-plugin.toml and herdr/tui/Cargo.toml, with a section for it in CHANGELOG.md. Once the new version reaches main, the release workflow tags it, makes the GitHub release with its changelog section as notes, and builds the cockpit binary for macOS and Linux, with the Herdr app half beside it, as release assets.
